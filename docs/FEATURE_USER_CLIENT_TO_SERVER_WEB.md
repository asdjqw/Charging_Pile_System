## 2. 项目分工与本次范围

项目原计划分工为：

| 分工 | 负责内容 | 当前情况 |
|---|---|---|
| A | Qt 用户客户端 | 已有主体功能，本次完成网络化接入并调整业务流程 |
| B | Qt 管理员/服务器 GUI | 已有管理界面，本次与实际服务器生命周期和数据库状态整合 |
| C | Socket、多线程、核心业务 | 本次完成主要剩余内容 |
| D | SQLite、Web 运营大屏 | 本次完成主要剩余内容 |
| E | 机器学习 | 尚未实现，仅保留数据库扩展位置 |

本次工作的核心目标不是要求单独部署一台物理服务器，而是在同一台计算机上运行用户端和
管理/服务器端，通过真实的本地 TCP/HTTP 通信验证客户端与服务端边界。同时保留环境变量，
使服务端以后可以监听局域网地址，客户端也可以连接另一台 Ubuntu 设备。

## 3. `feature/User_client` 基线情况

### 3.1 已有能力

`feature/User_client` 已经建立了 Qt6/CMake 项目骨架，主要包含：

- Qt Widgets 用户客户端；
- Qt Widgets 管理端；
- SQLite 数据模型、初始化脚本和示例数据；
- 站点、电桩、用户、订单等基础管理能力；
- 用户登录、附近站点、导航、个人资料、充值和模拟充电界面；
- 管理员登录、营收概览、电桩状态和基础 CRUD 界面；
- 北京市充电站 CSV 数据导入能力；
- Ubuntu 构建与依赖安装脚本。

### 3.2 基线的关键限制

该分支 README 已明确说明用户端仍属于单机演示实现。虽然目标架构要求只有服务器访问
SQLite，实际用户端仍通过 `DatabaseManager` 直接读写数据库，存在以下问题：

1. 用户端和管理端没有真正通过 Socket 协作，无法验证 C 分工要求的网络协议与并发处理。
2. SQLite 文件可能被多个进程直接打开，业务入口和事务边界分散。
3. 预约、充电、结算、状态变化等逻辑主要依附于界面，缺少统一服务端校验。
4. 管理端只是 GUI 程序，还没有承担 TCP/HTTP 服务器职责。
5. Web 运营大屏尚未实现，无法通过浏览器查看运营数据。
6. 缺少协议测试、数据库行为测试和跨进程业务冒烟测试。

因此，本次改造以 `feature/User_client` 的 UI 和数据模型为基础，不推翻已有界面，而是补齐
服务器、协议和 Web 层，并将数据库所有权收敛到服务端。

## 4. 当前总体架构

```text
Qt 用户客户端
    |
    | TCP 9000：长度帧 + UTF-8 JSON
    v
Qt 管理端 / 本地服务器 ---- SQLite 数据库
    ^
    | HTTP 8080：静态资源 + JSON API
    |
Web 运营大屏（浏览器）
```

当前架构的核心约束如下：

- 用户客户端不再直接打开 SQLite；
- Web 页面不直接访问数据库；
- `admin_server` 是数据库、TCP 服务和 HTTP 服务的唯一入口；
- 客户端通过 TCP `9000` 调用业务接口；
- 大屏通过 HTTP `8080` 获取静态页面和实时汇总数据；
- 默认只监听 `127.0.0.1`，适合单机演示与开发测试；
- 可通过配置改为监听 `0.0.0.0`，用于局域网联机。

这种设计让“客户端和服务端在同一设备上运行”与“客户端、服务端分布在不同设备上运行”
使用同一套代码路径，单机运行并不是绕过服务器，而是把网络回环地址作为真实通信链路。

## 5. C 部分：Socket、多线程与核心业务改动

### 5.1 TCP 帧协议

新增 `common/FramedJson.h/.cpp`，为 TCP 字节流提供明确的消息边界：

```text
[4 字节大端无符号长度][UTF-8 JSON 数据]
```

选择长度帧而不是按换行拆分，可以正确处理粘包、拆包和一条消息分多次到达的情况。协议测试
会将多个帧拼接并分段输入，确认解析器能够恢复完整 JSON 消息。

### 5.2 请求与响应格式

新增 `common/JsonCodec.h/.cpp`，统一模型与 JSON 的转换。请求包含：

```json
{
  "version": 1,
  "requestId": "客户端生成的唯一编号",
  "action": "stations.list",
  "token": "登录后会话令牌",
  "data": {}
}
```

响应保留相同 `requestId`，并通过 `ok`、`code`、`message` 和 `data` 表达处理结果。客户端
据此匹配同步请求，服务端也能返回可展示的业务错误，而不是只断开连接。

### 5.3 本地 TCP/HTTP 服务器

新增 `admin_server/LocalServer.h/.cpp`，在一个服务对象中管理：

- TCP 监听和多客户端连接；
- 每个连接的接收缓冲区和帧解析状态；
- JSON 请求转发；
- HTTP 请求解析；
- Web 静态文件分发；
- HTTP API 到内部业务动作的映射；
- 服务停止时的连接和监听器清理。

服务器对象被移动到独立 `QThread`。网络线程负责监听、收发和帧处理，业务分发通过 Qt
信号/槽回到拥有数据库连接的主线程，响应再以队列调用发送到网络线程。这样既避免 GUI 被
网络 I/O 阻塞，也避免跨线程错误使用同一个 Qt SQL 连接。

### 5.4 统一业务分发器

新增 `admin_server/ApiDispatcher.h/.cpp`，将 TCP 和 HTTP 请求映射到统一数据库业务接口。
当前主要动作包括：

| 领域 | 动作 |
|---|---|
| 服务 | `server.health` |
| 用户 | `user.login`、`user.phoneLogin`、`user.register`、`user.get`、`user.update` |
| 钱包 | `wallet.recharge` |
| 站点 | `stations.list`、`stations.districts` |
| 电桩 | `piles.list`、`piles.get` |
| 预约 | `reservation.create`、`reservation.cancel`、`reservation.active` |
| 充电 | `charge.start`、`charge.progress`、`charge.stop`、`charge.ongoing` |
| 订单 | `orders.list` |
| 大屏 | `dashboard.summary`、`dashboard.stations` |

除健康检查、登录注册和公开大屏接口外，用户业务请求需要有效会话令牌。服务器保存登录会话
与用户标识的映射，拒绝缺少或失效令牌的请求。

### 5.5 核心业务规则

数据库层集中实现了以下主要规则：

- 手机号不存在时可以自动创建用户并登录；
- 冻结用户不能继续预约或充电；
- 同一用户不能同时拥有多个有效预约；
- 只有空闲电桩可以预约；
- 预约默认 15 分钟有效，过期后恢复电桩状态；
- 用户只能取消自己的有效预约；
- 余额不足 10 元时不能开始充电；
- 同一用户不能同时存在多个进行中订单；
- 已被预约的电桩只能由对应预约用户开始充电；
- 充电进度、电量、金额和遥测数据持续持久化；
- 结束充电时在事务内结算、扣费、记录流水并恢复电桩状态；
- 业务失败时回滚事务，避免订单、余额和电桩状态部分更新；
- 预约号与订单号由时间信息加 UUID 片段生成，避免同一毫秒并发创建时重复。

### 5.6 客户端网络 API

新增 `user_client/ServerApiClient.h/.cpp`，封装：

- 服务地址和端口；
- TCP 连接和自动错误提示；
- 请求编号生成；
- 长度帧编码与响应解析；
- 会话令牌保存；
- 请求超时；
- 用户、站点、电桩、预约、充电、充值和订单的类型化调用。

`LoginDialog` 和 `MainWindow` 已改为通过 `ServerApiClient` 完成用户业务。客户端启动时不再
初始化数据库，也不再依赖 SQLite 驱动；管理端/服务器关闭后，客户端会明确提示无法连接，
而不会静默读取本地数据库。

## 6. D 部分：SQLite 与 Web 大屏改动

### 6.1 数据库所有权与初始化

数据库默认保存于：

```text
~/.local/share/ChargePileLab/charge_pile.db
```

只有 `admin_server` 在启动时调用 `DatabaseManager::initialize()`。初始化过程负责建表、种子
数据和 CSV 站点数据导入，并通过兼容性迁移补齐旧数据库缺少的字段或索引。

本次在原有模型上补强了用户状态、电桩状态日志、预约、订单进度、钱包流水、管理员审计和
大屏汇总查询，并新增站点编码和充值支付号的条件唯一索引，降低重复业务数据风险。

### 6.2 数据库事务边界

事务重点覆盖以下复合操作：

- 创建预约：写入预约记录并将电桩置为 `reserved`；
- 取消/过期预约：更新预约状态并释放电桩；
- 开始充电：消费有效预约、创建订单并将电桩置为 `charging`；
- 更新进度：同步订单进度与遥测记录；
- 停止充电：完成订单、扣减余额、写入钱包流水并释放电桩；
- 冻结用户：检查进行中订单、处理有效预约并写审计日志；
- 远程重启电桩：校验状态、写状态变化和管理员审计记录。

这些规则现在位于数据库/服务端层，Qt 客户端或 Web 页面无法通过界面绕过。

### 6.3 Web 静态资源服务

新增 `web/` 目录：

| 文件 | 作用 |
|---|---|
| `index.html` | 大屏结构和语义化内容 |
| `styles.css` | 响应式运营界面、状态与可访问性样式 |
| `app.js` | API 请求、图表更新、搜索、分页和错误状态 |
| `echarts.min.js` | 离线 ECharts 运行资源，不依赖公网 CDN |

`admin_server` 启动后直接提供这些资源，因此不需要 Node.js、npm、Nginx 或独立 Web 后端。
访问 `http://127.0.0.1:8080/` 即可打开大屏。

### 6.4 Web API

| 路径 | 功能 |
|---|---|
| `GET /api/health` | 检查服务和数据库状态 |
| `GET /api/dashboard?days=7` | 返回 KPI、7/30 日营收、电桩状态和最近订单 |
| `GET /api/stations?limit=20&offset=0&q=关键字&district=区域` | 分页搜索站点 |

当前 Web API 与页面来自同一来源，不涉及跨域配置。站点接口在数据库侧执行分页和搜索，浏览器
不会一次加载全部 3000 多个站点。

### 6.5 大屏功能与优化

当前大屏包含：

- 服务健康状态、当前时间和手动刷新；
- 今日营收、本月营收、在线率和异常电桩；
- 累计营收、订单、用户、站点及不同状态电桩数量；
- 近 7 日/30 日营收趋势切换；
- 电桩运行状态环形图；
- 最近订单表格；
- 站点名称、地址或区域搜索；
- 站点上一页/下一页分页与总量提示；
- 加载、空结果、服务错误和重试状态；
- 桌面和窄屏响应式布局；
- 键盘焦点、ARIA 标签和减少动画偏好支持。

站点较多时采用“服务端分页 + 搜索”而非全量加载。这样减少 SQLite 查询结果序列化、HTTP
传输、浏览器 DOM 节点和渲染开销，也更适合运营人员快速定位目标站点。

## 7. 管理端改动

管理端从单纯的数据库 GUI 提升为系统服务器宿主：

- 程序启动时初始化唯一 SQLite 连接；
- 自动启动 TCP `9000` 和 HTTP `8080`；
- 网络服务运行在独立线程；
- 管理员登录后进入原有管理界面；
- 窗口标题显示 TCP 和 Web 端口；
- 仪表盘、电桩、用户和订单数据从统一数据库状态刷新；
- 用户冻结/解冻和电桩模拟重启使用服务端业务校验及审计；
- 关闭管理端时有序停止监听器和网络线程；
- 支持 `CHARGE_PILE_HEADLESS=1`，无管理 GUI 只运行服务。

需要注意：非 headless 模式下，服务器在线不等于管理员已经登录。程序会先初始化数据库并启动
服务，再显示管理员登录窗口；取消登录会结束整个进程和服务。

## 8. 构建与跨平台兼容

项目以课程 Ubuntu 环境为兼容基准：

- Ubuntu 22.04；
- GCC/G++ 11.4；
- CMake 3.22.1；
- Qt 6.2.4；
- GNU Make 4.3；
- C++17。

本项目不依赖特定个人开发设备，也没有引入仅限某一桌面系统的核心业务依赖。Web 大屏使用
原生 HTML/CSS/JS 和本地 ECharts，Ubuntu 无需安装 Node.js。

顶层 CMake 会构建公共库、用户端、管理/服务器端和测试程序，并把数据库脚本、CSV 和 Web
资源复制到可执行文件附近。`scripts/build.sh` 默认使用 CMake Unix Makefiles，适配课程环境。

| 环境变量 | 默认值 | 用途 |
|---|---|---|
| `CHARGE_PILE_HOST` | `127.0.0.1` | 用户端连接的服务地址 |
| `CHARGE_PILE_PORT` | `9000` | TCP 业务端口 |
| `CHARGE_PILE_HTTP_PORT` | `8080` | Web 大屏端口 |
| `CHARGE_PILE_BIND_ADDRESS` | `127.0.0.1` | 服务监听地址 |
| `CHARGE_PILE_DB_PATH` | 系统应用数据目录 | 自定义 SQLite 文件路径 |
| `CHARGE_PILE_WEB_ROOT` | 程序旁的 `web` | 自定义 Web 静态资源目录 |
| `CHARGE_PILE_HEADLESS` | `0` | 设为 `1` 时只运行服务 |

局域网部署时，服务端可设置：

```bash
CHARGE_PILE_BIND_ADDRESS=0.0.0.0 ./build/admin_server/admin_server
```

其他设备上的客户端需要将 `CHARGE_PILE_HOST` 设置为服务器局域网 IP。还需要确认操作系统
防火墙允许 TCP `9000` 和 `8080`。默认配置仅允许本机访问，更适合课堂单机演示。

### 10.4 建议的人工验收流程

1. 启动 `admin_server`，确认终端显示 TCP `9000` 和 Web `8080` 已监听。
2. 使用 `admin / 123456` 登录管理端，检查营收、订单、电桩和用户数据。
3. 启动用户端，用一个 11 位手机号登录。
4. 搜索站点，选择空闲电桩并预约。
5. 取消一次预约，确认电桩恢复空闲。
6. 再次预约并开始充电，观察进度和服务端数据变化。
7. 停止充电，核对余额、钱包流水、订单金额和电桩状态。
8. 打开 `http://127.0.0.1:8080/`，检查 KPI、图表和最近订单是否更新。
9. 使用站点搜索和翻页，确认总量、页码和结果一致。
10. 关闭服务器，确认客户端显示连接失败且大屏无法继续请求数据。

## 12. 开发与测试注意事项

1. 必须先启动 `admin_server`，再启动用户端或打开 Web 大屏。
2. `9000` 或 `8080` 被占用时服务器会启动失败，应先关闭旧进程或通过环境变量换端口。
3. 改动数据库 schema 后应同时考虑已有数据库迁移，不能只修改全新建库脚本。
4. 不要让用户端重新链接 Qt SQL 或直接打开 SQLite，这会破坏当前架构边界。
5. 修改 TCP JSON 字段时，应同步更新 `JsonCodec`、`ApiDispatcher`、`ServerApiClient` 和测试。
6. 修改核心业务时，应优先在 `DatabaseManager` 中保持事务完整，再调整界面表现。
7. Web 大屏站点列表应继续使用服务端分页，避免把 3000 多个站点一次性渲染到 DOM。
8. 测试前应确认使用的是测试数据库；删除默认数据库会导致重新初始化，不应误删需要保留的数据。
9. 构建目录、运行数据库、日志和个人 IDE 配置不应提交到 Git。
10. 提交前至少执行一次干净构建、CTest 和完整预约到结算流程。
