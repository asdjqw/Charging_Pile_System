# 充电桩模拟数据扩容生成规则

> 所属仓库 `Charge_pile`。脚本：`bigscreen/spark/jobs/generate_expanded_data.py`。  
> 北京 POI 优先：`bigscreen/data/external/`，否则仓库根目录 `data/北京市充电桩数据.csv`。  
> 扩容结果是模拟数据，不是真实 5.5 万笔业务订单。

## 一、目的与适用范围

本项目原始数据只有 105 座充电站、3395 笔订单和 1594 条电池遥测，周末及夜间样本较少，
不足以充分展示区域分布、峰平谷负荷、用户分层等大屏分析效果。

`spark/jobs/generate_expanded_data.py` 在保留原始业务特征的基础上，融合北京市充电站 POI，
生成可供 Spark 清洗、统计分析和答辩演示使用的模拟扩容数据。

扩容数据是根据原始样本和业务约束生成的模拟数据，并非真实采集的 55000 笔业务订单。

## 二、输入数据

| 输入文件 | 内容 | 基础规模 |
| --- | --- | ---: |
| `data/raw/nvv2t.csv` | 充电订单 | 3395 笔 |
| `data/raw/dsv13r2.csv` | 电池遥测 | 1594 条 |
| `data/raw/nvv2t_md_end.csv` | 原充电站维度 | 105 座 |
| `../data/北京市充电桩数据.csv` | 北京市充电站 POI | 3024 条有效站点记录 |

北京 POI 默认按以下顺序自动查找：

1. `data/external/北京市充电桩数据.csv`；
2. `../data/北京市充电桩数据.csv`。

也可以通过 `--poi` 显式指定文件。

## 三、目标规模

默认参数为：

```text
目标订单总量：55000
周末目标概率：29%
新增订单遥测生成比例：45%
随机种子：20250914
```

订单数量计算：

```text
新增订单数 = 目标订单数 - 原始订单数
           = 55000 - 3395
           = 51605

最终订单数 = 3395 + 51605 = 55000
```

遥测数量计算：

```text
新增遥测数 = int(51605 × 45%) = 23222
最终遥测数 = 1594 + 23222 = 24816
```

一次使用默认参数的实际输出为：

| 数据 | 扩容后规模 |
| --- | ---: |
| 订单 | 55000 笔 |
| Spark 清洗后的有效订单 | 54944 笔 |
| 电池遥测 | 24816 条 |
| 北京充电站 | 3024 座 |
| 有订单的活跃站点 | 2993 座 |
| 充电桩 | 12026 台 |
| 活跃用户 | 2556 人 |

## 四、北京站点生成规则

脚本读取北京 POI 后，首先丢弃缺少 POI 编号、名称或区县的记录，并按 `POI_ID` 去重。

每座有效站点生成以下字段：

- `stationId`：从 100000 开始顺序生成；
- `locationId`：从 500000 开始顺序生成；
- `station_name`：区县与原 POI 名称组合；
- `address`：省、市、区县和 POI 地址组合；
- `open_time`：统一为 `00:00-24:00`；
- `device_count`：按权重分配 1、2、3、4、6、8、10 或 12 台设备。

### 4.1 站点类型

脚本优先根据名称或 POI 类型关键词判断：

| 关键词 | `facilityType` | 类型 |
| --- | ---: | --- |
| 超充 | 4 | 超充站 |
| 交直流 | 3 | 交直流充电站 |
| 直流、快充 | 2 | 直流充电站 |
| 交流、慢充 | 1 | 交流充电站 |

没有明确关键词时，按以下权重随机分配：

```text
直流站 50%，交直流站 25%，交流站 20%，超充站 5%
```

### 4.2 站点订单权重

新订单不会平均分配给所有站点，而是使用：

```text
站点抽样权重 = device_count ^ 1.25
```

充电桩越多的站点，被分配到订单的概率越高。

## 五、原始订单保留与站点映射

脚本保留原始 3395 笔订单的时间、用户、充电量、费用、平台和车队车辆标记等运营字段，
但会把原郑州站点的 `stationId`、`locationId` 和 `facilityType` 稳定映射到北京站点。

同一个原站点始终映射到同一个北京站点。因此更准确的答辩表述是：

> 保留原始订单的主要运营指标和时间特征，同时将站点外键映射到新的北京站点维度。

## 六、新订单时间规则

模拟订单日期范围固定为：

```text
2014-11-18 至 2015-10-04
```

每次生成订单时：

1. 按 `--weekend-rate` 决定生成工作日或周末订单，默认概率为 29%；
2. 在符合该日期类型的自然日中均匀选择一天；
3. 按小时权重选择开始小时；
4. 分钟和秒随机生成；
5. 根据充电时长计算结束时间。

小时权重重点覆盖：

- 8—11 点上午高峰；
- 18—20 点晚间高峰；
- 12—17 点日间平段；
- 0—6 点夜间谷段。

该规则用于补充原始数据中周末和夜间样本不足的问题。

为了兼容现有 Spark 清洗逻辑，输出时间仍使用原数据形式，例如 `0015-06-01`表示2015年，
后续由 ETL 统一修复年份。

## 七、充电量、时长和功率规则

### 7.1 充电量

从原始订单中随机抽取一个充电量，并加入随机扰动：

```text
新充电量 = 原样本充电量 × U(0.75, 1.30)
```

最终限制在 0.3—40 kWh。

### 7.2 充电时长

从原始时长中抽样并增加扰动：

```text
新充电时长 = 原样本时长 × U(0.70, 1.30)
```

最终限制在 0.1—11.5 小时。

### 7.3 功率约束

脚本通过以下约束确保平均单枪功率不超过 60 kW：

```text
充电时长 = max(模拟时长, 充电量 / 60)
```

该规则用于避免短时间内充入大量电量等明显不合理的记录。

## 八、充电费用规则

脚本先从原始订单计算：

- 原始付费订单比例；
- 已付费订单的每度电价格分布。

生成新订单时：

1. 按“原始付费率 × 1.6”决定是否收费；
2. 未命中付费概率时，费用为 0；
3. 付费订单从原始单价集合中抽取单价；
4. 单价再乘以 0.9—1.1 的随机扰动；
5. 按“充电量 × 单价”计算最终费用。

默认扩容结果中付费订单占比约为 17.56%。

## 九、用户生成规则

脚本生成 2500 个随机用户编号，并使用以下权重形成长尾分布：

```text
用户权重 = 1 / 用户序号 ^ 0.45
```

每笔新增订单选择用户时：

- 70% 概率从原始用户和前 120 名高频模拟用户中选择；
- 30% 概率从全部模拟用户池中选择。

这样可以形成少量高频用户和大量低频用户，为 RFM 用户价值分层提供更合理的样本。

## 十、平台及其他订单字段

| 字段 | 生成规则 |
| --- | --- |
| `sessionId` | 从 900000000 起随机递增，与原始订单号隔离 |
| `platform` | 按原始 iOS、Android、Web 比例抽样 |
| `managerVehicle` | 按原始车队车辆比例抽样 |
| `stationId` | 按站点设备权重抽取 |
| `locationId` | 使用选中站点的位置编号 |
| `facilityType` | 使用选中站点的类型 |
| `weekday` | 根据模拟日期生成 Mon、Tues 等 |
| `Mon`—`Sun` | 根据模拟日期生成星期独热字段 |

## 十一、电池遥测生成规则

默认给 45% 的新增订单生成一条电池遥测，`esd`等于对应订单的`sessionId`，以便后续关联。

| 指标 | 模拟范围或规则 |
| --- | --- |
| SOC | 15%—80% |
| 电池包电压 | 随 SOC 增长，并加入随机扰动 |
| 充电电流 | 22.5—75A，按原格式保存为负值 |
| 单体压差 | 以 10—32mV 为基础，并随 SOC 调整 |
| 最高温度 | 32—38℃ |
| 温差 | 1—2.5℃ |
| 可用能量 | 随 SOC 增长，限制在 6.5—34 |
| 可用容量 | 随 SOC 增长，限制在 21—100Ah |

`record_time`继续输出为原始格式`2.02E+13`，后续ETL将其识别为精度丢失字段并丢弃。

## 十二、可复现性

默认随机种子为：

```text
20250914
```

在输入文件和参数相同的情况下，重复执行会生成相同结果，便于开发测试、数据核对和答辩演示。

可以通过 `--seed`修改随机种子。

## 十三、执行命令

在 `bigscreen`目录执行：

```bash
.venv/bin/python spark/jobs/generate_expanded_data.py \
  --poi ../data/北京市充电桩数据.csv \
  --orders 55000 \
  --weekend-rate 0.29 \
  --telemetry-rate 0.45 \
  --seed 20250914
```

输出目录：

```text
data/raw_expanded/
├── nvv2t.csv
├── dsv13r2.csv
└── nvv2t_md_end.csv
```

验证文件行数：

```bash
wc -l data/raw_expanded/*.csv
```

预期为：

```text
24817  dsv13r2.csv        # 1行表头 + 24816条遥测
55001  nvv2t.csv          # 1行表头 + 55000笔订单
3025   nvv2t_md_end.csv   # 1行表头 + 3024座站点
```

## 十四、进入Spark分析链路

本地开发模式：

```bash
export SPARK_MASTER='local[*]'
.venv/bin/python spark/jobs/run_all.py --raw data/raw_expanded
.venv/bin/python spark/jobs/load_mysql.py
```

HDFS和YARN模式：

```bash
hdfs dfs -mkdir -p /data/charging/raw_expanded
hdfs dfs -put -f data/raw_expanded/*.csv /data/charging/raw_expanded/

export SPARK_MASTER=yarn
export PYSPARK_PYTHON=$PWD/.venv/bin/python
.venv/bin/python spark/jobs/run_all.py \
  --raw hdfs:///data/charging/raw_expanded \
  --warehouse hdfs:///data/charging/warehouse \
  --ads hdfs:///data/charging/ads
```

Spark清洗会剔除原始数据中保留下来的56条异常记录，因此大屏显示54944条有效订单，而不是55000条。

## 十五、局限性与答辩口径

该扩容方案适合教学实训和可视化演示，但存在以下边界：

1. 新增订单是统计模拟数据，不应表述为真实运营数据；
2. 北京站点名称和区县来自真实 POI，但设备数量、站点类型以及订单归属包含模拟成分；
3. 时段权重和周末比例包含人工业务规则，并非从完整真实历史数据训练得到；
4. 金额、时长、电池指标主要按经验分布抽样，不能用于真实计费或安全判断；
5. 固定随机种子保证可复现，不代表模型具有预测能力；
6. 该脚本是数据准备工具，机器学习预测属于后续独立功能。

推荐答辩表述：

> 项目以3395笔原始订单为基础，融合3024座北京充电站POI，从原始数据学习充电量、时长、单价、平台和车辆类型等经验分布，并加入周末、峰谷时段、用户长尾及最大功率约束，生成可复现的55000笔模拟订单。扩容数据随后进入HDFS，通过Spark on YARN完成清洗与15维分析。
