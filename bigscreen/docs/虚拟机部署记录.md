# 虚拟机部署记录（本仓库约定）

旧稿记录的是另一台机器上的 nginx + systemd `charging-screen`、HDFS `bitdev:9000`。**不要照抄 IP 和端口。**

## 推荐状态

| 项 | 约定 |
|---|---|
| 系统 | Ubuntu 22.04，普通用户（如 `bit`），不要 `sudo bash` 整份安装脚本 |
| 工程 | 共享盘 `/mnt/hgfs/Small_s3/Charge_pile`，运行时同步到 `$HOME` |
| 安装 | `scripts/setup_all_ubuntu.sh` |
| 日常 | `bash ~/start_charge_pile.sh` |
| 大屏 | Flask `127.0.0.1:5000`，库 `charging_screen` |
| Qt | TCP 9000，HTTP 8080 |
| ML 查询 | 5010，venv `$HOME/charging-ml-venv` |
| Hadoop | 3.3.6 伪分布式，RPC **8020**，`/data/charging` |

## 踩坑（仍然有效）

1. 共享盘 `noexec`：venv、Hadoop、Qt 二进制放 `$HOME`。
2. 系统是 `python3` 不是 `python`。
3. 分析大屏入口是 **5000** 不是 8080。
4. HDFS 不要占用 9000。
5. `ml/requirements.txt` 不适合 Ubuntu 自带 3.10。
6. 家目录快捷方式不会凭空出现，先 `install_start_shortcut.sh` 或完整 setup。

可选：在 `~/charging-bigscreen` 执行 `bash deploy/install_service.sh` 才会有 nginx 80 与开机 systemd。未做这一步就不要在答辩里说「80 端口 nginx」。

## 本次实测部署状态（192.168.44.129，bit@bitdev）

大屏与预测页都在这一台上跑通了，实际状态如下：

| 项 | 实测值 |
|---|---|
| 工程目录 | `/home/bit/Charging_Pile_System`（本机磁盘，非共享盘） |
| 大屏 | nginx 80 → Flask `127.0.0.1:5000`（systemd `charging-screen`），MySQL `charging_screen` 已连 |
| 预测页 | `http://192.168.44.129/#/forecast`，同源 `/api/forecast/latest` |
| ML 推理环境 | `$HOME/charging-ml-full`（Python 3.12.13 + `ml/requirements.txt`） |
| 模型 | 六个冻结模型已装在 `ml/artifacts/models/`（3.5 GB，来自 Release `ml-resources-20260914`，SHA256 已核对） |
| 预测批次 | `ml/data/warehouse/ads/measured_forecast.json`（MEASURED，绑定到 Qt 3024 座电站） |
| 查询服务 | `127.0.0.1:5010`（`ml/cli/warehouse_api`，systemd 未注册，由脚本 nohup 起） |

重算预测（数据更新或批次变旧时执行，任一段都可重复跑）：

```bash
cd /home/bit/Charging_Pile_System
bash scripts/run_measured_ml.sh          # 建快照 → 跑六个模型 → 发布批次 → 绑定 Qt ID → 重启 :5010
sudo systemctl restart charging-screen   # 让大屏重新解析批次目录（首次从 fixtures 切到 ads 时必须）
```

注意：`run_measured_ml.sh` 会把快照时间平移到“当前小时”，所以批次不会显示“数据偏旧”；
但业务明细本身是历史数据，模型对某些目标小时（如上午的 H1）会给出 0，这属于模型输出而非页面故障。
